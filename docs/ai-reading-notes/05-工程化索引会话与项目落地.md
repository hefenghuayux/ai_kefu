## 1. 工程化先看三类数据

这个项目里有三类核心数据：

```text
用户业务数据
  -> MySQL
  -> users / conversations / messages

结构化知识
  -> Neo4j
  -> Product / Order / Customer / Review 等节点关系

非结构化知识
  -> GraphRAG 索引产物
  -> entities / relationships / communities / text_units / community_reports
```

大模型只是推理层，真正能不能落地，取决于这些数据链路能否稳定维护。

## 2. MySQL 异步连接如何配置

看 `app/core/database.py`：

```python
engine = create_async_engine(
    settings.DATABASE_URL,
    echo=False,
    pool_pre_ping=True,
    pool_size=5,
    max_overflow=10
)
```

这里使用 SQLAlchemy 异步引擎。

关键配置：

- `pool_pre_ping=True`：请求前检测连接是否断开。
- `pool_size=5`：常驻连接池 5 个连接。
- `max_overflow=10`：连接池不够时最多额外创建 10 个。

也就是说并发下最多可以有 15 个数据库连接。

会话工厂：

```python
AsyncSessionLocal = sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False
)
```

后续服务层统一：

```python
async with AsyncSessionLocal() as db:
    ...
```

## 4. 会话保存流程

看 `conversation_service.py`。

创建会话：

```python
conversation = Conversation(
    user_id=user_id,
    title="新会话",
    dialogue_type=DialogueType.NORMAL
)
```

保存消息：

```python
user_content = next((msg["content"] for msg in messages if msg["role"] == "user"), "")
```

如果是第一条消息，用用户第一句话生成标题：

```python
if messages_count == 0:
    title = ConversationService.get_conversation_title(user_content)
    conversation.title = title
```

然后保存两条消息：

```python
user_message = Message(
    conversation_id=conversation_id,
    sender="user",
    content=user_content
)

assistant_message = Message(
    conversation_id=conversation_id,
    sender="assistant",
    content=response
)
```

这就是普通聊天的持久化链路：

```text
模型生成完成
  -> on_complete 回调
  -> ConversationService.save_message
  -> 保存 user message
  -> 保存 assistant message
```

## 5. LangGraph 会话和 MySQL 会话不是一回事

这一点很重要。

普通聊天的会话存在 MySQL：

```text
conversations
messages
```

LangGraph 的运行状态存在 checkpointer：

```python
checkpointer = MemorySaver()
graph = builder.compile(checkpointer=checkpointer)
```

接口里通过：

```python
thread_config = {
    "configurable": {
        "thread_id": thread_id,
        "user_id": user_id,
        "image_path": ...
    }
}
```

来恢复 LangGraph 状态。

当前 checkpointer 是 `MemorySaver`，意味着状态存在内存里。服务重启后，LangGraph 状态会丢失。

如果要生产可用，应考虑：

- SQLiteSaver
- PostgresSaver
- Redis/数据库持久化 checkpointer

## 6. 文件上传入口：`/api/upload`

看 `main.py`：

```python
@app.post("/api/upload")
async def upload_file(
    file: UploadFile = File(...),
    user_id: int = Form(...)
):
```

上传后目录设计：

```python
user_uuid = str(uuid.uuid5(uuid.NAMESPACE_DNS, f"user_{user_id}"))
first_level_dir = UPLOAD_DIR / user_uuid

timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
second_level_dir = first_level_dir / timestamp
```

文件名增加时间戳：

```python
new_filename = f"{original_name}_{timestamp}{ext}"
file_path = second_level_dir / new_filename
```

保存后构造 `file_info`：

```python
file_info = {
    "filename": new_filename,
    "original_name": file.filename,
    "size": len(content),
    "type": file.content_type,
    "path": str(file_path).replace('\\', '/'),
    "user_id": user_id,
    "user_uuid": user_uuid,
    "upload_time": timestamp,
    "directory": str(second_level_dir)
}
```

然后进入索引服务：

```python
indexing_service = IndexingService()
index_result = await indexing_service.process_file(file_info)
```

完整链路：

```text
用户上传文件
  -> 保存到 uploads/user_uuid/timestamp/
  -> 生成 file_info
  -> IndexingService.process_file
  -> GraphRAG build_index
  -> 返回 index_result
```

## 8. 用户级输入输出目录

`_prepare_user_directories`：

## 9. 文件复制和配置覆盖

上传文件先复制到 GraphRAG input：

```python
input_file_path = self._copy_file_to_input_dir(file_path, user_input_dir)
```

然后准备配置：

```python
config_overrides = {
    'input.base_dir': user_input_dir,
    'output.base_dir': user_output_dir,
    'input.file_pattern': f".*{os.path.basename(input_file_path)}$$"
}
```

这里的意思是：

- GraphRAG 只处理当前上传的这个文件。
- 输出写到当前用户的 output 目录。

加载配置：

```python
graphrag_config = load_config(
    Path(self.data_dir),
    Path(config_path),
    config_overrides
)
```

## 10. GraphRAG 索引构建

核心调用：

```python
index_result = await api.build_index(
    config=graphrag_config,
    method=IndexingMethod.Standard,
    is_update_run=is_update,
    memory_profile=False,
    progress_logger=progress_logger
)
```

这一步不是简单 embedding，而是 GraphRAG 的离线索引流程，通常包括：

```text
读取输入文档
  -> 文本切分
  -> 实体抽取
  -> 关系抽取
  -> 图构建
  -> 社区发现
  -> 社区报告
  -> 向量生成
  -> 输出 entities / relationships / text_units / communities / community_reports
```

项目里后续查询 GraphRAG 时加载的就是这些产物。

## 11. 为什么 GraphRAG 要离线构建

GraphRAG 查询时需要：

```python
entities = await load_table_from_storage("entities", self.storage)
text_units = await load_table_from_storage("text_units", self.storage)
communities = await load_table_from_storage("communities", self.storage)
community_reports = await load_table_from_storage("community_reports", self.storage)
relationships = await load_table_from_storage("relationships", self.storage)
```

这些东西不是用户提问时临时生成的。原因：

- 实体关系抽取要调用大模型，耗时高。
- 社区发现要跑图算法，不能实时做。
- 社区报告生成成本高。
- 向量化和落盘需要时间。

所以 GraphRAG 的工程模式是：

```text
离线阶段：
  文档 -> GraphRAG 索引产物

在线阶段：
  用户问题 -> 加载索引 -> local/global/drift/basic search -> 回答
```

## 12. 哪些能力适合实时，哪些适合预处理

适合实时：

- Router 意图识别
- Guardrails 判断
- Planner 任务拆分
- Tool Selection
- Text2Cypher 生成
- Cypher 查询
- Summarize 结果汇总

适合预处理：

- PDF 解析
- 长文档切分
- 实体抽取
- 关系抽取
- GraphRAG 社区发现
- 文本 embedding
- 高频 Cypher 模板沉淀

原因很简单：用户能接受 1-5 秒回答，但不能接受每次提问都重新构建知识图谱。

## 13. 搜索服务也是工程化补充能力

虽然五阶段重点不是联网搜索，但项目里还有 `/api/search`。

`search_service.py` 通过工具调用实现：

```python
self.tool_registry.register(FunctionTool(
    **SEARCH_TOOL,
    handler=self._handle_search
))
```

模型先决定是否需要搜索：

```python
response = await self.client.chat.completions.create(
    model=self.model,
    messages=query,
    tools=self.tool_registry.get_tools_definition(),
    tool_choice="auto"
)
```

如果 `finish_reason == "tool_calls"`，执行 SerpAPI 搜索，再把搜索结果交给模型总结。

这和 LangGraph 工具选择思想类似，只是这里是 OpenAI function calling 风格。

## 14. 当前工程实现的薄弱点

### 1. GraphRAG 索引更新判断较弱

```python
file_name = Path(file_path).stem
index_path = os.path.join(output_dir, f"{file_name}_index")
return os.path.exists(index_path)
```

但 GraphRAG 实际输出不一定是 `{file_name}_index` 这种目录结构。这个增量判断可能不准确。

### 2. `config_mapping` 未定义

`_get_config_file` 使用：

```python
return self.config_mapping.get(file_type, self.default_config)
```

但类里没有看到 `self.config_mapping` 初始化。如果调用该方法，会报属性错误。

### 3. `process_file` 异常返回中可能引用未定义变量

异常分支：

```python
return {
    'file_path': file_path,
    'status': 'error',
    'error': str(e)
}
```

如果异常发生在 `file_path = file_info['path']` 之前，`file_path` 可能未定义。

### 4. LangGraph 状态只存在内存

`MemorySaver` 不适合生产持久化。服务重启后会话状态消失。

### 5. 文件问答链路未完全接上

`main.py` 有 `/api/upload` 和 `/chat-rag`，但 `create_file_query` 是 `TODO`，`RAGChatService` 当前没有在扫描范围内看到定义。说明文件上传索引和 Agent 文件问答之间还不是完整闭环。

## 15. 你应该形成的工程理解

这个项目不是简单“调一个大模型接口”，而是把大模型放进一个业务系统：

```text
模型层：
  DeepSeek / Ollama / Vision Model / Embedding Model

编排层：
  LangGraph / Router / Planner / Tool Selection

知识层：
  Neo4j / GraphRAG / FAISS / Redis Cache

业务层：
  FastAPI / MySQL / 用户会话 / 文件上传
```

工程化学习重点不是“每个库怎么用”，而是：

- 什么东西实时做。
- 什么东西离线做。
- 什么东西缓存。
- 什么东西持久化。
- 什么东西需要评估。
