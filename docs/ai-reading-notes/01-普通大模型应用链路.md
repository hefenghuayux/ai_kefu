# 第一阶段：普通大模型应用链路

本阶段目标：先不碰复杂 Agent、RAG 和图数据库，只搞懂一件事：用户在前端发一句话，为什么后端能调用 DeepSeek 或 Ollama，并把模型输出逐字流式返回给前端。

对应代码：

- `deepseek_agent/llm_backend/main.py`
- `deepseek_agent/llm_backend/app/core/config.py`
- `deepseek_agent/llm_backend/app/services/llm_factory.py`
- `deepseek_agent/llm_backend/app/services/deepseek_service.py`
- `deepseek_agent/llm_backend/app/services/ollama_service.py`

## 1. 配置层：`.env` 如何决定使用哪个模型

先读 `app/core/config.py`。

核心类是：

```python
class ServiceType(str, Enum):
    DEEPSEEK = "deepseek"
    OLLAMA = "ollama"

class Settings(BaseSettings):
    DEEPSEEK_API_KEY: str
    DEEPSEEK_BASE_URL: str
    DEEPSEEK_MODEL: str

    OLLAMA_BASE_URL: str
    OLLAMA_CHAT_MODEL: str
    OLLAMA_REASON_MODEL: str
    OLLAMA_EMBEDDING_MODEL: str
    OLLAMA_AGENT_MODEL: str

    CHAT_SERVICE: ServiceType = ServiceType.DEEPSEEK
    REASON_SERVICE: ServiceType = ServiceType.OLLAMA
    AGENT_SERVICE: ServiceType = ServiceType.DEEPSEEK
```

这里把大模型服务分成三类：

- `CHAT_SERVICE`：普通聊天接口 `/api/chat` 使用。
- `REASON_SERVICE`：深度思考接口 `/api/reason` 使用。
- `AGENT_SERVICE`：LangGraph Agent、Router、Planner、GraphRAG 工具链使用。

这点很重要。项目不是“全局只用一个模型”，而是按功能划分模型来源：

```text
普通聊天      -> CHAT_SERVICE
深度思考      -> REASON_SERVICE
Agent 编排    -> AGENT_SERVICE
Embedding 缓存 -> OLLAMA_EMBEDDING_MODEL
视觉模型      -> VISION_MODEL
```

`Settings.Config` 指定：

```python
env_file = str(ENV_FILE)
env_file_encoding = "utf-8"
case_sensitive = True
```

所以 `.env` 文件中的变量名必须和 `Settings` 字段大小写一致。比如：

```env
CHAT_SERVICE=deepseek
REASON_SERVICE=ollama
AGENT_SERVICE=deepseek
```

如果你写成 `CHAT_SERVICE=DEEPSEEK`，由于枚举值是小写字符串，可能会解析失败。

## 2. 工厂层：`LLMFactory` 解决了什么问题

读 `app/services/llm_factory.py`：

```python
class LLMFactory:
    @staticmethod
    def create_chat_service():
        if settings.CHAT_SERVICE == ServiceType.DEEPSEEK:
            return DeepseekService()
        else:
            return OllamaService()

    @staticmethod
    def create_reasoner_service():
        if settings.REASON_SERVICE == ServiceType.DEEPSEEK:
            return DeepseekService()
        else:
            return OllamaService()

    @staticmethod
    def create_search_service():
        return SearchService()
```

它把“接口层”和“模型供应商细节”隔开。

如果没有工厂，`main.py` 里就会到处写：

```python
if settings.CHAT_SERVICE == ...
```

现在变成：

```python
chat_service = LLMFactory.create_chat_service()
```

接口层只关心“我要一个聊天服务”，不关心它来自 DeepSeek 还是 Ollama。

这对大模型项目很常见，因为模型供应商经常变化：

- 开发环境可能用本地 Ollama。
- 生产环境可能用 DeepSeek API。
- 后续可能换 Qwen、OpenAI、火山、智谱。

工厂模式让替换成本集中在一个文件里。

## 3. FastAPI 接口层：为什么返回 `StreamingResponse`

看 `main.py` 的 `/api/chat`：

```python
@app.post("/api/chat")
async def chat_endpoint(request: ChatMessage):
    chat_service = LLMFactory.create_chat_service()

    return StreamingResponse(
        chat_service.generate_stream(
            messages=request.messages,
            user_id=request.user_id,
            conversation_id=request.conversation_id,
            on_complete=ConversationService.save_message
        ),
        media_type="text/event-stream"
    )
```

这里有三个关键点：

1. `generate_stream(...)` 是异步生成器，不是一次性返回字符串。
2. `StreamingResponse` 会边生成边把内容发给前端。
3. `media_type="text/event-stream"` 表示这是 SSE 格式。

SSE 的数据格式通常长这样：

```text
data: "你"

data: "好"

data: "呀"
```

前端拿到一个 chunk 就追加到聊天气泡里，所以用户会看到“逐字输出”的效果。

## 4. DeepSeek 调用链：OpenAI 兼容接口 + 流式输出

读 `app/services/deepseek_service.py`。

初始化：

```python
self.client = AsyncOpenAI(
    api_key=settings.DEEPSEEK_API_KEY,
    base_url=settings.DEEPSEEK_BASE_URL
)
self.model = settings.DEEPSEEK_MODEL or model
```

DeepSeek 走的是 OpenAI 兼容接口，所以代码使用 `openai.AsyncOpenAI`。

真正调用模型的位置：

```python
response = await self.client.chat.completions.create(
    model=self.model,
    messages=messages,
    stream=True
)
```

`stream=True` 是流式返回的核心。

后面逐块读取：

```python
async for chunk in response:
    if chunk.choices and chunk.choices[0].delta.content:
        content = json.dumps(chunk.choices[0].delta.content, ensure_ascii=False)
        full_response.append(content)
        yield f"data: {content}\n\n"
```

你可以把它理解成：

```text
DeepSeek token stream
  -> Python async for 逐块读取
  -> yield SSE data
  -> FastAPI StreamingResponse
  -> 前端逐步展示
```

注意：这里 `full_response.append(content)` 保存的是 `json.dumps` 之后的字符串，不是原始文本。因此最终拼出来的 `complete_response` 可能包含额外的 JSON 引号。后续如果做会话存储质量优化，这里值得检查。

## 5. Ollama 调用链：本地 HTTP 接口

读 `app/services/ollama_service.py`。

Ollama 不走 OpenAI SDK，而是直接调用 HTTP：

```python
async with session.post(
    f"{self.base_url}/api/chat",
    json={
        "model": model,
        "messages": messages,
        "stream": True,
        "keep_alive": -1,
        "options": {
            "temperature": 0.7,
        }
    }
) as response:
```

然后逐行读取：

```python
async for line in response.content:
    chunk = json.loads(line)
    if content := chunk.get("message", {}).get("content"):
        full_response.append(content)
        content = json.dumps(content, ensure_ascii=False)
        yield f"data: {content}\n\n"
```

Ollama 的流式响应通常是一行一个 JSON，因此这里是 `json.loads(line)`。

DeepSeek 和 Ollama 的差异：

| 项目 | DeepSeek | Ollama |
|---|---|---|
| 调用方式 | `AsyncOpenAI` SDK | `aiohttp` 请求本地服务 |
| 流式字段 | `chunk.choices[0].delta.content` | `chunk["message"]["content"]` |
| 模型来源 | 在线 API | 本地模型 |
| 配置字段 | `DEEPSEEK_*` | `OLLAMA_*` |

## 6. 会话保存：为什么要传 `on_complete`

`/api/chat` 调用时传了：

```python
on_complete=ConversationService.save_message
```

在 DeepSeek 服务里，模型完整输出结束后：

```python
if on_complete and user_id is not None and conversation_id is not None:
    await on_complete(user_id, conversation_id, messages, complete_response)
```

这表示保存会话不是接口层直接做，而是模型服务在“完整答案生成完毕”后回调保存。

这样设计的原因是：流式输出时，接口函数本身很快就返回了 `StreamingResponse`，真正的生成过程在异步生成器内部持续发生。只有生成器读完所有 chunk 后，才知道完整回复是什么。

## 7. Redis 语义缓存在普通聊天中的位置

`DeepseekService.generate_stream` 开始时会创建用户级缓存：

```python
cache = RedisSemanticCache(prefix="deepseek", user_id=user_id)
cached_response = await cache.lookup(messages)
```

如果命中缓存：

```python
async for chunk in self._stream_cached_response(cached_response):
    yield chunk
```

如果没命中，才调用模型：

```text
用户消息
  -> RedisSemanticCache.lookup
    -> 命中：模拟流式输出缓存答案
    -> 未命中：调用 DeepSeek
      -> 生成完整答案
      -> RedisSemanticCache.update
```

缓存这部分第三阶段会详细讲。这里先知道它插在模型调用之前，用来减少重复问题的推理成本。

## 8. 你应该能解释的完整链路

以 `/api/chat` 为例：

```text
前端发送 messages、user_id、conversation_id
  -> main.py /api/chat
  -> LLMFactory.create_chat_service()
  -> 根据 CHAT_SERVICE 返回 DeepseekService 或 OllamaService
  -> generate_stream(...)
  -> 先查 Redis 语义缓存
  -> 未命中则调用模型流式接口
  -> 每个 chunk 包装成 SSE: data: xxx\n\n
  -> StreamingResponse 返回前端
  -> 生成完毕后调用 ConversationService.save_message
```

一句话总结：

> 这个阶段的核心不是“模型有多聪明”，而是把模型输出接成一个稳定的后端流式服务。

## 9. 阅读时要注意的工程细节

1. `DeepseekService` 有缓存，`OllamaService` 当前没有接入 Redis 语义缓存。
2. DeepSeek 和 Ollama 的流式协议不同，所以服务类不能简单共用一个实现。
3. `on_complete` 回调只有在流式生成完成后才会执行。
4. `complete_response` 拼接的内容可能包含 JSON 转义后的片段，后续做数据清洗时要留意。
5. `/api/reason` 也走 `LLMFactory`，但用途是“推理模式”，默认配置是 `REASON_SERVICE=ollama`。

## 11. 本阶段方案的不足

这个阶段只覆盖了“普通聊天服务”的工程链路，还没有解释模型为什么会选择工具、为什么能查知识库、为什么能拆任务。因此它适合打基础，但不能代表项目的核心竞争力。项目真正有区分度的部分在第二阶段之后：Prompt 控制、结构化输出、LangGraph 编排、Text2Cypher 和 GraphRAG。
