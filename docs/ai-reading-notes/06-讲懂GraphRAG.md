# 讲懂 GraphRAG：从普通 RAG 到图增强检索

## 0. 一句话先讲清楚

GraphRAG 不是“把知识图谱接到 RAG 后面”这么简单。它的核心思想是：

```text
先把大规模文档离线加工成图结构和社区摘要，
再在查询时根据问题类型选择不同粒度的上下文，
让 LLM 能回答跨文档、跨实体、全局总结和多跳关联问题。
```

普通 RAG 更像“从文档堆里找相似片段”。GraphRAG 更像“先把文档整理成知识地图，再按问题去地图上找局部区域或全局概览”。

## 1. GraphRAG 主要解决什么问题

普通向量 RAG 的典型流程是：

```text
用户问题
  -> embedding
  -> 向量库召回 top-k chunk
  -> 把 chunk 放进 prompt
  -> LLM 生成答案
```

这个流程适合回答局部事实问题，例如：

```text
智能门锁 S1 的保修期是多久？
```

因为只要召回到包含“智能门锁 S1 + 保修期”的文本片段，LLM 就能回答。

但它不擅长三类问题：

1. 全局总结问题：例如“用户对智能家居产品最常见的不满是什么？”
2. 多跳关联问题：例如“哪些产品同时涉及安装复杂、售后慢和退货率高？”
3. 隐藏主题发现问题：例如“这些售后记录背后反映出哪些系统性问题？”

这些问题不一定能靠 top-k 相似片段解决。因为答案可能分散在很多文档、很多实体、很多关系中。向量检索只看“问题和片段的语义相似度”，不天然知道哪些实体之间存在关系，也不天然知道整个语料库的主题结构。

GraphRAG 的目标就是补上这件事：

```text
不只找相似文本，还要理解实体、关系、社区和全局结构。
```

## 2. GraphRAG 的核心设计：离线索引 + 在线查询

理解 GraphRAG 最重要的是先分清两个阶段：

```text
离线索引阶段：把文档加工成可检索的图结构和摘要结构。
在线查询阶段：根据问题选择合适的索引产物组织上下文。
```

这两个阶段不能混在一起理解。GraphRAG 的很多成本、优势和局限都来自离线索引阶段。

## 3. 离线索引阶段：每一步解决什么问题

### 3.1 文档分块：把长文档变成可处理单元

原始文档可能很长，LLM 和 embedding 模型不能无限读取，所以第一步要切成 text units，也就是文本块。

它解决的问题是：

```text
把长文档拆成模型能处理、能索引、能回溯来源的基本单元。
```

它引入的代价是：

```text
chunk 太小会丢上下文，chunk 太大会增加成本并降低召回精度。
```

什么时候不该过度依赖它：

```text
如果问题本身需要跨很多 chunk 的全局判断，只靠文本分块和向量召回就不够。
```

### 3.2 实体和关系抽取：从文本里抽出图结构

GraphRAG 会从 chunk 中抽取实体、关系、实体描述、关系描述。

例如：

```text
文本：智能门锁 S1 经常出现指纹识别失败，用户反馈售后响应较慢。

实体：
  - 智能门锁 S1
  - 指纹识别失败
  - 售后响应

关系：
  - 智能门锁 S1 -> 出现问题 -> 指纹识别失败
  - 用户反馈 -> 指向 -> 售后响应较慢
```

它解决的问题是：

```text
把非结构化文本变成实体和关系，方便后续发现跨文档关联。
```

它引入的代价是：

```text
抽取质量依赖 LLM。实体漏抽、关系错抽、同义实体没有合并，都会影响后续图质量。
```

什么时候不该用：

```text
如果文档很少、结构很简单，直接向量 RAG 或结构化数据库查询可能更划算。
```

### 3.3 社区发现：把紧密相关的实体聚成主题区域

GraphRAG 会对实体关系图做社区发现，常见算法是 Leiden。社区可以理解为：

```text
图中连接更紧密的一组实体和关系。
```

例如智能门锁的故障、安装、保修、用户评价可能形成一个社区；智能音箱的联网、语音识别、固件升级可能形成另一个社区。

它解决的问题是：

```text
把大量实体关系组织成多个主题区域，让系统知道语料库里有哪些知识板块。
```

它引入的代价是：

```text
社区划分不一定等于业务人员心中的分类。图噪声越大，社区结果越不稳定。
```

什么时候不该过度相信它：

```text
当实体关系抽取本身很噪时，社区发现只是把噪声重新聚类，不会自动变正确。
```

### 3.4 社区报告：把一片图压缩成可读摘要

社区报告是 GraphRAG 的关键产物。它不是普通 chunk 摘要，而是对一个社区内部实体、关系和证据的综合报告。

可以把它理解成：

```text
一个主题区域的结构化摘要。
```

它解决的问题是：

```text
把大量原文和图关系压缩成更高层的知识单元，方便回答全局问题。
```

它引入的代价是：

```text
摘要会损失细节，也可能继承或放大前面抽取阶段的错误。
```

什么时候不该只看社区报告：

```text
当用户问非常具体的原文事实、编号、金额、时间、条款时，应该回到 text_units 或结构化数据，而不是只靠报告摘要。
```

## 4. 在线查询阶段：GraphRAG 怎样回答问题

离线阶段结束后，GraphRAG 通常会得到这些索引产物：

```text
text_units           原文文本块
entities             实体
relationships        实体关系
communities          社区
community_reports    社区报告
covariates           可选的附加事实或声明
vector_store          向量索引
```

在线查询不是每次都重新抽实体、重新建图，而是加载这些已经构建好的产物，根据问题类型组织上下文。

## 5. 四种搜索模式的边界

### 5.1 Basic Search：传统向量搜索

Basic Search 接近普通 RAG。

```text
问题
  -> 向量召回相关 text_units
  -> LLM 基于文本块回答
```

适合：

```text
具体事实查询、文档片段定位、简单说明问答。
```

例如：

```text
智能门锁 S1 的电池规格是什么？
```

解决的问题：

```text
快速从原文中找相似片段。
```

代价和不足：

```text
不擅长全局总结，也不擅长跨多个实体的关系推理。
```

什么时候不该用：

```text
当问题需要综合整个语料库趋势时，只召回 top-k chunk 容易片面。
```

### 5.2 Local Search：围绕实体的局部图检索

Local Search 的核心是：

```text
先找和问题相关的实体，
再围绕这些实体组织邻近关系、原文块和社区报告。
```

它不是单纯图遍历，也不是单纯向量检索，而是混合上下文构建。

在本项目使用的 GraphRAG API 中，local search 会依赖：

```text
entities
relationships
text_units
community_reports
covariates 可选
```

适合：

```text
围绕具体实体、产品、故障、政策、评价的问答。
```

例如：

```text
智能门锁 S1 经常出现哪些故障？相关售后处理方式是什么？
```

解决的问题：

```text
比普通向量 RAG 更能围绕实体聚合相关证据。
```

代价和不足：

```text
依赖实体识别和实体召回。如果问题里的实体没有被正确抽取，local search 可能找不到正确上下文。
```

什么时候不该用：

```text
当问题不是围绕具体实体，而是要求全局趋势、整体主题、跨社区比较时，local search 的视野可能太窄。
```

### 5.3 Global Search：基于社区报告的全局综合

Global Search 的核心上下文不是原始 chunk，而是 community_reports。

它的典型思想是：

```text
把每个社区报告当成一个高层知识单元，
先分别判断不同社区与问题的关系，
再综合多个社区的发现形成全局答案。
```

这就是常说的 map-reduce：

```text
Map 阶段：
  对一批 community_reports 分别生成局部观察、相关事实或中间答案。

Reduce 阶段：
  把多个局部结果去重、合并、排序、归纳，形成最终答案。
```

例如：

```text
问题：智能家居产品的主要售后问题集中在哪些方面？

Map：
  社区 A：智能门锁集中在指纹识别失败、电池续航差。
  社区 B：智能音箱集中在联网失败、语音唤醒不稳定。
  社区 C：摄像头集中在安装复杂、隐私设置不清楚。

Reduce：
  售后问题主要集中在识别/连接稳定性、续航、安装配置、隐私说明四类。
```

动态社区选择则是在 global search 里进一步控制上下文：

```text
不是固定读取所有某一层级社区报告，
而是根据问题挑选更相关的社区进入综合过程。
```

适合：

```text
全局总结、主题归纳、跨文档趋势分析、跨实体共性问题总结。
```

解决的问题：

```text
避免普通 RAG 只看少数 top-k chunk 导致答案片面。
```

代价和不足：

```text
社区报告是压缩后的摘要，可能丢失细节。全局综合还会消耗更多 LLM 调用和 token。
```

什么时候不该用：

```text
当用户问具体事实、具体条款、具体产品参数时，global search 可能太粗，容易给出概括性答案。
```

### 5.4 DRIFT Search：从局部问题向相关社区扩展

DRIFT Search 可以理解为介于 local 和 global 之间的方式。

它不是一上来就做全局总结，而是：

```text
先围绕问题做局部搜索，
再根据局部结果和相关社区继续扩展上下文。
```

适合：

```text
问题从一个实体出发，但可能需要向相关主题扩展。
```

例如：

```text
智能门锁 S1 的差评是否和整个门锁品类的售后问题有关？
```

这个问题既有具体实体，也需要扩展到相关社区趋势。

解决的问题：

```text
避免 local search 视野太窄，同时避免 global search 一开始就过度发散。
```

代价和不足：

```text
控制难度更高，扩展方向可能受中间结果影响。如果前面局部检索偏了，后续漂移也会跟着偏。
```

什么时候不该用：

```text
当问题很明确、只需要一个事实时，不需要 DRIFT。它会增加复杂度和成本。
```

## 6. 四种模式快速对比

| 模式   | 核心上下文                                      | 最适合               | 主要代价             | 不该用于           |
| ------ | ----------------------------------------------- | -------------------- | -------------------- | ------------------ |
| Basic  | text_units                                      | 简单事实、片段问答   | 视野窄               | 全局趋势、多跳综合 |
| Local  | entities + relationships + text_units + reports | 围绕实体的问答       | 依赖实体抽取和召回   | 宏观总结           |
| Global | community_reports                               | 全局总结、跨文档归纳 | 摘要损失细节、成本高 | 具体事实查询       |
| DRIFT  | local context + related communities             | 从实体出发的扩展分析 | 控制复杂、可能漂移   | 简单明确问题       |

## 7. 和普通 RAG 的本质区别

普通 RAG 的基本问题是：

```text
哪些文本片段和问题最相似？
```

GraphRAG 的问题是：

```text
这个问题涉及哪些实体、关系、社区和全局主题？
应该用原文片段、局部图邻域，还是社区报告来回答？
```

所以 GraphRAG 的提升不只是多了知识图谱，而是多了一套“知识组织层级”：

```text
chunk 级：回答具体事实
entity 级：围绕实体聚合证据
relationship 级：解释实体之间的关联
community 级：总结一片知识区域
global 级：综合多个社区形成整体答案
```

## 8. 在本项目里的位置

本项目里 GraphRAG 不是唯一检索方式，而是多工具智能客服系统中的一个工具。

### 8.1 索引构建入口

`deepseek_agent/llm_backend/app/services/indexing_service.py` 负责把上传文件复制到用户输入目录，并调用 GraphRAG 的 `api.build_index` 构建索引。

关键流程是：

```text
上传文件
  -> 判断 MIME 类型
  -> 准备用户 input/output 目录
  -> 复制文件
  -> 加载 settings.yaml
  -> 覆盖 input.base_dir、output.base_dir、input.file_pattern
  -> api.build_index(...)
```

这说明项目里的 GraphRAG 索引是“先构建、后查询”的。它不是用户一问问题才临时读 PDF。

### 8.2 查询执行入口

`deepseek_agent/llm_backend/app/lg_agent/kg_sub_graph/agentic_rag_agents/components/customer_tools/node.py` 中的 `GraphRAGAPI` 会加载已经构建好的索引产物：

```text
entities
text_units
communities
community_reports
relationships
covariates 可选
```

然后根据配置选择查询模式：

```text
GRAPHRAG_QUERY_TYPE = local / global / drift / basic
```

当前项目默认配置是：

```text
GRAPHRAG_QUERY_TYPE: "local"
GRAPHRAG_COMMUNITY_LEVEL: 3
GRAPHRAG_DYNAMIC_COMMUNITY: False
```

这意味着项目默认更偏向“围绕实体的局部检索”，而不是默认做全局总结。

### 8.3 和 Neo4j / Cypher 的分工

本项目还有 Neo4j、预定义 Cypher、Text2Cypher。不要把它们和 GraphRAG 混成一件事。

更合理的分工是：

```text
价格、库存、订单、分类、明确字段
  -> 预定义 Cypher 或 Text2Cypher

售后政策、维修说明、产品评价、故障描述、说明书问答
  -> GraphRAG

复杂问题同时包含结构化数据和非结构化知识
  -> LangGraph Planner 拆任务，再分别调用 Cypher 和 GraphRAG
```

例如：

```text
问题：智能门锁 S1 库存还有多少？如果指纹模块坏了能不能退？

任务 1：库存还有多少？
  -> Cypher 查询结构化库存字段

任务 2：指纹模块坏了能不能退？
  -> GraphRAG 查询售后、维修、退换货文档
```

## 9. 常见误解

### 误解 1：GraphRAG 就是知识图谱问答

不准确。GraphRAG 的重点不是直接在图数据库上跑查询，而是用图结构帮助组织检索上下文。它可以使用文件形式的索引产物、Parquet 表、向量库和社区报告，不一定等于 Neo4j 查询。

### 误解 2：GraphRAG 一定比普通 RAG 好

不准确。GraphRAG 更适合复杂知识库和全局问题。对于小文档、简单事实、低成本场景，普通向量 RAG 更直接。

### 误解 3：Global Search 可以回答所有问题

不准确。Global Search 擅长全局综合，但不擅长具体事实。它看的是社区报告，细节可能已经被摘要压缩掉。

### 误解 4：有了社区报告就不需要原文

不准确。社区报告适合宏观理解，原文 text_units 仍然是具体证据来源。严肃问答里最好能回溯原文。

## 10. 学代码时应该抓住的主线

不要一开始钻进 `app/graphrag` 的所有内部实现。更高效的阅读顺序是：

```text
1. indexing_service.py
   先理解索引从哪里构建，产物输出到哪里。

2. customer_tools/node.py
   再理解查询时加载哪些表，如何选择 local/global/drift/basic。

3. graphrag/api/query.py
   最后看不同 search API 分别需要哪些输入表。

4. lg_builder.py + multi_tool workflow
   回到项目主链，理解 GraphRAG 只是多工具 Agent 中的一个工具。
```

这条线能避免被上游 GraphRAG 的大量内部模块带偏。

## 11. 一句话复述版

GraphRAG 的价值在于：它先把文档组织成实体、关系、社区和社区报告，再根据问题选择局部实体上下文或全局社区摘要来回答，从而弥补普通向量 RAG 在全局总结、多跳关系和跨文档综合上的不足。

## 12. 合理性批判 / 不足分析

1. 成本更高：GraphRAG 的离线索引需要 LLM 抽取实体、关系和社区报告，构建成本明显高于普通 RAG。
2. 错误会累积：实体抽错、关系抽错、社区划分不合理、社区报告摘要失真，都会影响最终答案，而且排查链路更长。
3. 不适合所有问题：对简单事实查询、实时变化数据、结构化字段查询，GraphRAG 可能不如向量 RAG、数据库查询或 Cypher 直接。
4. 工程复杂度更高：需要管理输入目录、输出目录、索引版本、用户隔离、配置文件、向量库和 GraphRAG 产物。
5. 在本项目中还要注意：GraphRAG 只是多工具链的一环，不能把所有客服问题都交给 GraphRAG，否则会增加成本并降低结构化查询的稳定性。
